# 經驗庫（EXPERIENCE.md）

每個候選一筆：改了什麼 → 結果 → 判定 → 副作用 → 教訓。提新候選前先讀這份，避免重走失敗的路。
（policy-agent-demo 的經驗也適用：結構性改法通常勝過 prompt 叮嚀，但要實測；隱藏組錯題不能拿來改。）

## 第 0 輪：v0（第一版，沒看過錯題）

- result: 調整組 19/28（評分修正後），平均 3.6 秒
- 錯題分類：
  1. 整數相除：`SUM(d1_retained) / SUM(cohort_size)` 在 SQLite 是整數除法 → 留存率全是 0%（2 題）。摘要還照寫「皆為 0%」，數字檢查擋不到（0 確實在表格裡）
  2. 問題沒提日期，模型自己加 `date = '2026-09-30'` 或只查 8～9 月（3 題）
  3. 活動名稱沒有對照 → 模型反問 short_code；追問題跟著錯（2 題）
  4. 版本上線日沒給，「3.5.0 版上線當天到 8 月底」只查了 8 月（1 題）
  5. 照抄範例的 GROUP BY 結構，JOIN 錯欄位 → 查無資料 → 回「沒資料」（1 題）
- grader fix：「哪個國家 ARPDAU 最高」回 'US' 是對的，原本只收「美國」。改成代碼和名稱都算，所有候選 rescore

## 第 1 輪

- candidate: v1a（prompt 補規則：比率乘 1.0、沒提日期不要加日期、JOIN 用同義欄位）
  result: 23/28（+4）
  verdict: 有幫助。修好沒提日期的題目
  side effect: 無新錯題
  lesson: **「比率要乘 1.0」寫在 prompt 完全沒用**，模型照抄範例和 schema 裡的公式（SUM/SUM）。範例的影響力比規則大
- candidate: v1b（程式：活動名稱對照、版本附上線日、「到 N 月底」、沒提日期明講查全期間；查無資料先自檢一次）
  result: 23/28（+4）
  verdict: 有幫助。修好活動名稱、追問、版本上線日、CPI 最低
  side effect: 「TikTok 點擊率」「那它的點擊率呢」從「查無資料」變成「查得到但整數相除 = 0」— 本來就錯，只是錯的方式換了
  lesson: 查無資料自檢（EMPTY_RETRY）沒修好東南亞那題：模型檢查後輸出同一條錯的 SQL。8B 模型自我檢查能力有限

## 第 2 輪

- candidate: v2a（Compose v1a ＋ v1b ＋ 程式把 `SUM(a) / SUM(b)` 改寫成 `1.0 * SUM(a) / SUM(b)`）
  result: 27/28
  verdict: 有幫助。整數相除的 4 題（D1、D7、TikTok 點擊率、追問點擊率）全修好
  lesson: prompt 叮嚀沒用的錯，用程式改寫一次到位。這類「語言規則」的錯（SQLite 整數除法）最適合程式修
- candidate: v2b（v2a ＋ 範例換成含「地區 JOIN」「比率乘 1.0」的版本，範例題不取自調整組）
  result: 27/28
  verdict: 跟 v2a 同分。東南亞那題從「JOIN 錯 → 查無資料」進步到「地區過濾對了，但分組錯」
  side effect: 無
  lesson: 範例會被整段照抄（包含 GROUP BY 結構），換範例能改變模型的寫法

## 第 3 輪

- candidate: v3（v2b ＋ prompt：每日平均的子查詢只 GROUP BY date）
  result: 27/28，同一題仍錯（照樣 GROUP BY date, app_id）
  verdict: 沒幫助，淘汰。最終選 v2b（v2a 同分，但 v2b 在剩下那題錯得比較接近，範例也示範了正確寫法）
  lesson: 又一次證明 8B 模型照抄範例的力道大於規則文字。下一步可試：範例裡放一題「地區每日平均（不分組）」，或程式偵測「問題沒說各 App，SQL 卻 GROUP BY app_id」

- grader fix（看了隱藏組結果才發現，要老實講）：「各廣告活動的 CPI」模型用 short_code 當名稱，原本評分只收 campaign_name。改成短網址代碼也對應到活動名稱，所有候選 rescore（v0 13→14、v2b 16→17）。只改評分規則，沒有改任何 prompt 或程式流程
